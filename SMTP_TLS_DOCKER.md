# Diagnóstico SMTP/TLS en Docker de desarrollo

## Estado

Fecha: 2026-10-21. Rama `dev`, commit inicial `9a881e19deb545acee78e5cce67ca6c0169c50ea`.
El bloqueo quedó resuelto en el entorno actual después de que el usuario desactivó Norton. Los cuatro contenedores verifican TLS con código cero y autentican por SMTP. Django y un worker Celery enviaron un único correo de desarrollo, cuya recepción confirmó el usuario. No se instaló ninguna CA privada ni se relajó la validación TLS.

## Causa demostrada

Norton Email Protection intercepta SMTP y reemplaza la cadena del servidor por una firmada por **Norton Web/Mail Shield Root**. El host Windows confía en esa raíz; los contenedores Debian no. No es una raíz de Brevo. Actualizar las CA públicas no permite confiar automáticamente en ella.

Evidencia independiente:

1. OpenSSL dentro de backend, worker, chatbot y beat presenta una cadena de dos certificados que termina en Norton.
2. Windows, con validación estricta y el hostname SMTP efectivo, valida esa misma cadena y negocia TLS 1.3 / TLS_AES_256_GCM_SHA384.
3. El almacén raíz de Windows y el archivo oficial `C:\ProgramData\Norton\Antivirus\wscert.der` contienen la misma raíz y huella.
4. [Norton documenta ese archivo y el problema con almacenes de confianza separados](https://support.norton.com/sp/en/us/home/current/solutions/v20240108183457190). No se obtuvo la raíz de la conexión para instalarla.

## Opción A: excepción SMTP específica

El administrador del equipo debe revisar Norton Email Protection / escaneo SSL-TLS del correo y su política para los destinos SMTP configurados. Si la versión permite excepciones por destino, excluir únicamente la inspección de esos destinos, manteniendo la protección general y STARTTLS de Django. No cambiar las opciones TLS de la aplicación ni aceptar certificados inválidos. Si Norton no ofrece esa excepción, usar el método de CA oficial o consultar su soporte; no improvisar cambios de registro ni apagar toda la protección.

Después debe repetirse la sonda en los cuatro servicios. Exigir cadena pública confiable, SAN correcto y código cero, no simplemente que desaparezca un error de interfaz.

## Opción B: CA oficial, verificada y autorizada solo para desarrollo

La ruta oficial PEM localizada es `C:\ProgramData\Norton\Antivirus\wscert.pem`. Su equivalente DER fue comparado con el almacén de Windows: ambos tienen la huella indicada arriba y no contienen clave privada. Aun así, la confianza adicional requiere la autorización del responsable del entorno; no se instaló automáticamente.

La infraestructura preparada consta de:

- `BACKEND/Dockerfile.smtp-dev`: imagen derivada exclusivamente de desarrollo.
- `docker-compose.smtp-ca.dev.yml`: opt-in explícito para los cuatro servicios de correo.
- `scripts/install_smtp_ca.py`: rechaza claves privadas, bundles, huellas incorrectas, certificados no CA, fechas inválidas y firmas inválidas.
- Secret de BuildKit: certificado público externo al contexto Git; no se copia desde la conexión SMTP.

La huella esperada se proporciona fuera del código. No se descubre automáticamente ni se acepta por coincidencia con una conexión interceptada. La instalación usa `update-ca-certificates`; no modifica CERT_REQUIRED ni check_hostname. Una vez incorporada, la imagen de desarrollo confiará en esa CA para las conexiones que usan el almacén del sistema, no solo una conexión SMTP: esa ampliación explica la autorización requerida. Nunca usar este override en producción ni distribuir la imagen privada como imagen productiva.

Ejemplo conceptual, ejecutar únicamente tras validar procedencia y autorización:

```powershell
# Variables de la sesión; nunca contraseñas ni .env en el comando.
$env:SMTP_LOCAL_CA_PATH='<ruta oficial al certificado público PEM>'
$env:SMTP_LOCAL_CA_SHA256='<huella SHA-256 confirmada por fuente independiente>'
docker compose -f docker-compose.dev.yml -f docker-compose.smtp-ca.dev.yml build backend celery-worker celery-chatbot celery-beat
docker compose -f docker-compose.dev.yml -f docker-compose.smtp-ca.dev.yml up -d --no-deps backend celery-worker celery-chatbot celery-beat
```

La base frontend-backend:latest debe construirse primero con el Dockerfile público actualizado. No se guardan certificados locales en Git. `.local-certs/` y `BACKEND/certs/local/` están excluidos; se recomienda utilizar directamente la exportación oficial externa. El certificado incorporado es público, no una clave privada; las imágenes resultantes son específicas del entorno.

## Diagnóstico reproducible

```powershell
docker compose -f docker-compose.dev.yml exec -T backend python scripts/smtp_tls_diagnostics.py
# Repetir en celery-worker, celery-chatbot y celery-beat.
```

El script comprueba DNS, TCP, SMTP, STARTTLS, almacén de Python y OpenSSL, SAN/SNI y huellas. No autentica, no envía correo, no imprime certificados completos ni credenciales. Devuelve código de salida no cero si TLS no es válido.

Equivalente OpenSSL dentro del contenedor, usando el hostname efectivo:

```sh
openssl s_client -starttls smtp -connect smtp-relay.sendinblue.com:587 \
  -servername smtp-relay.sendinblue.com -verify_hostname smtp-relay.sendinblue.com \
  -showcerts -verify_return_error
```

Solo cuando los cuatro servicios validen TLS:

1. `python manage.py check_transactional_smtp`, con `--technical-visits` y `--password-reset` según corresponda: verifica STARTTLS y autenticación, sin RCPT ni DATA.
2. Abrir/cerrar la conexión real de Django para confirmar la misma ruta de confianza.
3. Enviar un único canario explícito mediante el servicio real y worker, a la cuenta autorizada, con asunto de prueba, sin CC/BCC ni datos reales. Ampliar a otros tipos solo si se necesita validar remitentes distintos.
4. Registrar aceptación SMTP e identificador del mensaje sin publicar enlaces ni tokens.
5. Solicitar confirmación humana de recepción; la aceptación SMTP por sí sola no demuestra llegada a la bandeja.

No modificar el estado de una compra/visita para forzar correos reales ni generar pagos o despachos. Si el transporte queda validado pero un remitente es rechazado, documentar ese error por separado y verificar el remitente en Brevo; no sustituirlo por otro.
