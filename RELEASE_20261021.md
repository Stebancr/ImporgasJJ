## Secuencia y rollback

1. Checks del PR aprobados, diff revisado y sin secretos; merge normal, sin reescritura.
2. Confirmar servidor limpio y respaldo verificado. `git fetch` y `git pull --ff-only origin main`; comprobar HEAD.
3. Actualizar claves privadas estrictamente necesarias; `docker compose config --quiet`, sin imprimir entorno.
4. Construir solo imágenes de aplicación afectadas. Ejecutar `migrate --plan` desde la nueva imagen contra la base existente y revisar antes de `migrate --noinput`.
5. Recrear únicamente aplicación/worker/gateway/proxy que lo requieran; conservar PostgreSQL, Redis, Ollama y volúmenes de datos.
6. Verificar HTTPS, estáticos/logo/media, API, permisos, WebSocket, SMTP estricto, destinatario único autorizado y prueba TCC interna. Sin pagos ni guías reales.
7. Comparar tablas/media, reinicios, logs y recursos; registrar commit e imágenes efectivos en el PR/informe final. Sincronizar dev con el merge de main sin reset.

Condiciones de rollback: productos inaccesibles, totales incorrectos, errores generalizados, migración inesperada/destructiva o contenedores inestables. Conservar evidencia y desactivar TCC. Las imágenes anteriores están etiquetadas como `imporgas-rollback-<servicio>:release-20261021`; usar un override Compose restringido que fije esas imágenes y `--no-build --no-deps` para recrear solo aplicación. Recuperar la configuración privada respaldada solo si se requiere. Mantener todas las columnas y volúmenes. No ejecutar migraciones inversas ni restaurar PostgreSQL sin autorización adicional.

Los resultados posteriores, commit de merge/despliegue y cualquier incidencia se registran en el PR #7 y en el informe de entrega. Una corrección de código debe originarse en dev, probarse y pasar por PR; nunca editar código en el servidor.
